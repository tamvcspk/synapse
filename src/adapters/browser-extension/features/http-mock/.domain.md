# Domain — `http-mock`

**What it is:** intercept requests a page makes and block, rewrite, or fake the response — the
"HTTP Error Mocker" panel, and the `net.mock` capability exposed to user scripts.

Read this before changing anything in `features/http-mock/`. Gotchas are in `docs/LESSONS.md`;
shipped history and fixed bugs are in `docs/CHANGELOG.md` §2.6. **This file owns the business rules.**

Scope name: `net.mock`, and it **requires `match`** — a mock rule without a resource dimension would
mean "intercept anything anywhere."

## Three mechanisms, one config shape

`MockConfig` is one shape; the `mechanism` field picks how it is enforced. **They are not
interchangeable** — each buys something and costs something:

| | `main-world` | `debugger` | `dnr` |
|---|---|---|---|
| Patches | page's `fetch`/XHR only | everything, via CDP | everything, declaratively |
| Shows in DevTools Network | ❌ | ✅ | ✅ |
| Chrome shows a debug banner | ❌ | ⚠️ **yes, permanently** | ❌ |
| Per-request JS callback | ✅ | ✅ | ❌ **none** |
| `delayMs` possible | ✅ | ✅ | ❌ |
| Body rewrite | ✅ | ✅ | URL + headers only |

**The constraint matrix is business policy, enforced in `validateMockConfig`.** A combination that
cannot work must be rejected at save time with a reason — never accepted and silently ignored.
Fields that a mechanism cannot honour are hidden in the UI via `showWhen`, so the user never
configures something that will not happen. `delayMs` under `dnr` was exactly this bug: accepted,
stored, silently dropped.

## What a script may choose — and may not

`net.mock.add` accepts an `action` (`'fake-response' | 'rewrite-request' | 'block'`) plus a couple of
hints (`rewriteBody`, `matchAnyResourceType`) — **the platform still always chooses the mechanism**
(`chooseMechanismForScriptRule`, `shared/http-mock.ts`); `mechanism` is never a field a script can
set. `api-inventory.md` §3.2 states this as a rule, not an implementation detail.

`rpc-handler.ts` runs the exact same `chooseMechanismForScriptRule` call, on the exact same
`req.args`, BEFORE dispatch — so the mechanism the enforce boundary checks against can never drift
from the mechanism `net-mock-host.ts`'s `performMockAdd` actually persists (docs/ROADMAP.md Track
B2b). `performMockAdd` trusts that check already happened and never re-verifies it — `rpc-handler.ts`
is the one enforce point (§3.4), a downstream host module is never trusted to self-limit.

The resolution policy, and why:
- `action: 'block'` → always `'dnr'`. It already catches every resource type (see
  `utils/dnr-network-rules.ts`'s `ALL_RESOURCE_TYPES` — that default exists FOR parity with
  `'debugger'`), at no banner cost. There is no case where `'block'` needs `debugger`.
- `action: 'rewrite-request'` → `'main-world'` whenever `rewriteBody` is set (the cheapest mechanism
  that can touch a request body at all) and `matchAnyResourceType` is unset; `'dnr'` when
  `matchAnyResourceType` is set but no body is being rewritten (redirect + header-modify need no body
  access); `'debugger'` ONLY when both are set together — the one real, common gap neither cheaper
  mechanism can close: rewriting the body of a bundled `<script src>` or a large `<img>` served
  straight from an HTML tag, since `main-world`'s patch only ever sees `fetch`/XHR calls and `dnr`
  cannot touch a body for any resource type.
- `action: 'fake-response'` → unchanged from v1, always `'main-world'`.

**The one `'debugger'`-resolving combination requires the ADDITIONAL scope `net.mock.debugger`** —
Chrome shows a permanent "debugging this tab" banner the user cannot miss, so its consent line names
that banner explicitly. A script that already declared `net.mock` for an origin only needs
`net.mock.debugger` AS WELL to unlock that one combination there, not a second origin list (same
`match` dimension, reused).

Consequence, accepted and documented: the builtin panel is the **master switch**. Turning it off
disables `net.mock` for every script, because both share one rule collection and one MAIN-world
payload rather than standing up a second parallel stack.

**Parity status (docs/ROADMAP.md Track B2b, shipped):** every `action`×`mechanism` combination a
script can reach through `net.mock.add` maps to exactly one of `main-world`/`dnr`/`debugger` — see
above. A deliberate loss, not silently dropped: file-upload rewrite/fake bodies
(`rewriteBodyFile`/`fakeResponseFile`, blob-backed) and `hitCountLimit`/`requestMatchContains` stay
Management-View-only — there is no file picker or typed-match-string concept meaningful to a script
API, matching the narrower-than-the-human-panel pattern established elsewhere in this codebase.

## Rule ownership

A rule created by a script carries `ownerModuleId`. It stays **visible** in the management UI (the
user can always see and delete what a script did on their behalf) but its owner field is hidden from
the edit form. **Every save path must preserve `ownerModuleId`** — dropping it on one edit orphans
the rule permanently, and orphaned rules keep matching traffic with no visible owner.

## Interception only applies from the next navigation

The MAIN-world interceptor is registered via `chrome.scripting`, which does **not** retroactively
apply to already-open tabs. A rule added now takes effect on that tab's **next load**. This is not a
bug to fix; it is a property to communicate, and any test or docs that assume otherwise are wrong.

## Binary correctness

Request-rewrite and response-fake both accept uploaded files. `bodyEncoding` (`'utf8' | 'base64'`)
must travel with the body on **both** directions; without it, base64 content gets re-encoded as
though it were text and every binary file silently corrupts. Storage differs by mechanism —
`debugger` keeps a blob reference in IndexedDB, `main-world` inlines base64 (2 MB cap) — and
**orphaned blobs must be swept whenever a rule's file is replaced or the rule is deleted.**
