# Domain — `secrets`

**What it is:** let a script use an API key without ever being able to read it.

Read this before changing `features/secrets/`. Architecture is in `docs/design.md` §12; shipped
history is in `docs/CHANGELOG.md` §11.6. **This file owns the business rules — and this feature has
more rules expressed as deliberate absences than as code.**

Scope name: `secrets.use`. There is **no** `secrets.read`, by design.

## The premise everything follows from

**If a script can read a secret, there is no security.** It has `fetch`; the next line exfiltrates.
A store that hands back plaintext protects roughly as much as pasting the key into the source — it
changes where the value sits, not who can read it.

So the script only ever holds a **name**. The platform substitutes the value at the **network
boundary**, in the background, and returns only the response. Same shape as media header replay:
the extension knows a header the page and script never see.

## Four deliberate absences — do not "complete the API"

1. **No `secrets.read` scope exists at all.** A scope that does not exist cannot be granted by
   mistake, misconfigured, or socially engineered out of a user.
2. **No create/update/delete API.** Secret management is UI-only, in the Dashboard. A script cannot
   seed its own secret and therefore cannot pre-stage an exfiltration target.
3. **No list API.** A secret's *name* is information too. A script declares the refs it needs and
   gets yes/no — it never enumerates.
4. **No at-rest encryption, and the Help page says so plainly.** Encrypting with a key stored beside
   the ciphertext is theater. A passphrase-derived key in `chrome.storage.session` would be real
   protection against profile theft, but it costs an unlock every session and kills unattended runs
   — a possible opt-in later, not v1. **The entire permission model rests on not lying to the user;
   claiming protection this design does not provide would break more than it fixes.**

## Three independent checks, all mandatory

A resolved secret must pass **all three**. They are independent on purpose — each answers a
different question, and collapsing any two loses a real guarantee.

| # | Check | Question it answers | Where |
|---|---|---|---|
| 1 | caller's `net.request` scope + `match` | may this script call this URL at all? | `rpc-handler.ts` |
| 2 | caller holds `secrets.use` | may this script use secrets at all? | `rpc-handler.ts`, special-cased |
| 3 | secret's own `allowedHost` matches the URL | may *this secret* go to this host? | `secret-resolution.ts` |

**Check 3 is a property of the secret, not of the caller**, so it runs for **every** transport —
not only at the RPC boundary like 1 and 2. Without it, a script with a legitimate broad `match`
could point a request at its own server and the `Authorization` header would ride along.

**Check 2 is special-cased in the RPC handler rather than being a fixed scope on the method**,
because it depends on the *shape of the arguments* — it applies only when a header value (or an
`ai.ask` option) actually contains a `secretRef`. A method-level scope cannot express that.

`secrets.use` deliberately carries **no `match` of its own**: the host dimension is already pinned
by the secret's `allowedHost`, and a second list describing the same fact is just two things that
can drift apart.

## The value must never travel backwards

A resolved secret appears in the outgoing request and **nowhere else** — not in the response object,
not in an error message. Errors may name the secret and the host it is bound to; they must never
include its value. Check this whenever you touch error construction here.

## Why this Module has a `uiSchema` at all

`SecretsModule` is a collection-schema Module **purely to borrow the generic management UI**, not
because it is a capability scripts can invoke. It declares no `scopes` and has no entry in
`API_METHODS`, so nothing reaches it through `synapseApi`. The only path from a script to a secret
is indirect, via a `{secretRef}` in a `net.request` header.

It needs `needs: ['bus', 'cache']` — **`bus` is not optional.** Without it the Kernel never
registers its listener, saves vanish silently, and the list stays empty with no error shown.
