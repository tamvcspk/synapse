# Domain — `media`

**What it is:** detect media (video/audio/stream) a page requests, list it, and download it —
including HLS streams that arrive as thousands of segments rather than one file.

Read this before changing anything in `features/media/`. Architecture is in `docs/design.md`;
gotchas are in `docs/LESSONS.md`; what already shipped and which bugs were fixed is in
`docs/CHANGELOG.md` §4–§8, §10. **This file owns the business rules only.**

Scope name: `media`. Read/download are deliberately **one** scope — splitting them would be a
two-prompt ritual where everyone allows both.

## Detection: three sources that disagree, on purpose

| Source | Sees | Blind to |
|---|---|---|
| `chrome.webRequest` | real URLs, real `initiator`, response headers | anything the page never requests over the network |
| DOM scan | `<video>`/`<audio>` already rendered | media loaded but not yet in the DOM |
| MAIN-world hooks (MSE/HLS) | `blob:` players that never expose a URL | players not using MSE or a known library |

**They are expected to disagree, and that is not a bug.** webRequest sees the true initiator of an
ad iframe while the DOM sources only ever see the top page URL, so the same stream can be filtered
by one path and admitted by another. Never "fix" this by forcing one source's view onto another.

**Trust rules for rejecting junk** — the whole point is that a naive "does the URL end in .mp4"
check drowns the list in ad/tracker noise:
- `resourceType === 'media'` → trust `Content-Type` first, fall back to the URL extension.
- Noisy types (`xmlhttprequest`, `object`, `other`) → require a genuinely matching `Content-Type`,
  **except** `.m3u8`/`.mpd`, which are trusted by extension alone.
- Segment extensions (`.ts`, `.m4s`) are **deliberately excluded** — they are parts of a stream that
  is already listed, and listing them would bury the real entry.
- `thirdParty` is a **label, not a filter.** Legitimate media is very often third-party (CDN).

## Scoping: exact page, not origin — and still not narrow enough

The Side Panel lists media for the **exact `tabUrl`**, not the origin. Origin scoping was shipped
first and rejected after real use: every video ever seen anywhere on a site piled into the list the
moment you opened any page of that site. Accepted trade-off: an SPA route change can hide an entry
detected just before the change.

**Known-insufficient, fix planned (ROADMAP Track A1).** `tabUrl` does not change on a reload, so
reloading a page keeps every entry from the previous load *and appends the new ones* — while the old
URLs have usually expired (signed URLs; see below). The detected-media list is **navigation-scoped
state** wearing permanent storage, and the fix is to key it to a navigation commit rather than to
`tabUrl`. Do not paper over this with more read-time filtering.

## Variants

A master playlist lists several resolutions. The UI shows **one** entry with a resolution picker,
never N sibling entries — `collapseVariantShadowedEntries` is the single place that decides this,
and any new consumer must go through it so a script sees exactly what the Side Panel sees.

## Downloading: four job kinds, one control surface

| Kind | When | Resumable after a crash? |
|---|---|---|
| VOD (HLS) | fixed segment list | ✅ checkpoint every 20s |
| Live (HLS) | media sequence grows, no `#EXT-X-ENDLIST` | ❌ **deliberately not** |
| Turbo (Range) | single large file, server supports ranges, opt-in | ❌ |
| — | master playlist | rejected: pick a variant first |

**Live capture is not "VOD with more segments."** There is no total, so identify segments by
**absolute media sequence**, never by array index — the sliding window makes an index point at a
different segment on the next poll. Stopping is *graceful finish* (flush the queue, then remux
exactly like VOD), which is different from Cancel (discard).

**Live is deliberately not checkpointed.** A checkpoint requires `commit()`, whose cost is O(file
size); on a recording with no final size that cost grows without bound.

**A failed segment means different things per kind.** VOD: fail the job — a hole makes the file
wrong. Live: log and skip — one lost segment must not end a multi-hour recording.

## Encryption boundary — do not blur it

AES-128 (`#EXT-X-KEY`) is **decryptable** and supported, including keys that rotate mid-playlist.
SAMPLE-AES and real DRM (Widevine/PlayReady) are **hard-refused with a clear message**. Never
attempt a partial download of DRM content "to see how far it gets" — it produces a corrupt file the
user has to diagnose.

## Signed URLs

URLs carrying expiry/signature tokens are **labelled, never blocked**. Mid-download 401/403 triggers
one manifest refetch and an index remap — budgeted **once per download**, and **only for VOD**
(remapping by index is exactly what a live sliding window makes meaningless).

## Correlation is best-effort — say so

Anchoring a badge to the right `<video>` for MSE/HLS players is unreliable and has survived three
rounds of fixes. It is an **open problem** (`docs/ROADMAP.md` `[§7.3-open]`), and the escape hatch
is the `media.correlate-url` pipeline slot letting a user script solve it for their own site.
Detection and download do **not** depend on it — they go through webRequest and work regardless.
Do not add a fourth speculative fix without debugging on a real page first.
