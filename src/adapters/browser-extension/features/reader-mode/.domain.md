# Domain — `reader-mode`

**What it is:** turn the current page — or a whole site — into readable Markdown with its images,
downloadable as a ZIP.

Read this before changing `features/reader-mode/`. Shipped history is in `docs/CHANGELOG.md` §1 and
§9.1. **This file owns the business rules.**

Uses no Enforced scope of its own: it reads the page (`page.dom`, Disclosed) and fetches images.
That is why it is the reference case proving the public API is sufficient — the whole feature is
reproducible from a user script using `lib.readable` + `lib.toMarkdown` + `net.request` + `lib.zip`
+ `files.save`, with no privileged call.

## The pipeline is four steps, and the split is load-bearing

`load-dom` → `clean` → `fetch-images` → `convert-markdown`

- **`clean` uses `@mozilla/readability`, not a hand-written heuristic.** Article extraction is a
  solved problem with a decade of edge cases baked in; do not reimplement it.
- **`fetch-images` runs in the content script**, so image requests carry the page's own credentials
  and referer — fetching them from the background would fail on any hotlink-protected host. Cap
  ~10 MB per image, dedupe by URL.
- **`convert-markdown` rewrites `src`/`href` from a `Map<absoluteUrl, localPath>`.** Relative URLs
  must be resolved to absolute *before* this step or the ZIP's links break once extracted.

**All four steps share one execution context on purpose** — a live `Document` is passed between
them. That object cannot cross a `structured-clone` boundary, so any proposal to move a step to
another context changes every step's signature. This is the concrete reason the roadmap refuses a
DAG engine whose nodes could span contexts.

## Crawl policy

- **Same-origin only**, hard cap `MAX_CRAWL_PAGES = 200`.
- Discovery order: `robots.txt` → `sitemap.xml` → expanding in-page navigation.
- Pages are fetched with `fetch()` + `DOMParser`, **not** by navigating tabs — that is what lets the
  exact same `clean`/`fetch-images`/`convert-markdown` code run per page.
- **One file per page**, never one concatenated document. Paths come from the URL structure so the
  output mirrors the site.

## Trigger placement is a decision, not an accident

Triggering lives **on the page** (two floating icons), not in the popup. The popup version shipped
first and was wrong twice over: it threw the user out of the page they were reading before any
result existed, and it pushed the very tab being crawled into the background — precisely when
Chrome is most likely to throttle or discard it. Progress and results go to the Side Panel, which
survives navigation.

Do not move the trigger back into the popup.

## Result handoff

Content scripts have no IndexedDB access worth relying on for large blobs, so results are handed to
a privileged page (Side Panel or Review tab) which stores images in IndexedDB and small text in
`chrome.storage.session`. A ZIP is built by the repo's own writer (`shared/zip.ts`, STORE method, no
dependency); "Download ZIP" and "Open in new tab" must reuse the **same** stored blobs and
`reviewId` rather than regenerating, or the two paths can disagree about what the user is looking at.
